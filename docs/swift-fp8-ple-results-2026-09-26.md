# Swift PLE FP8 转换与输出诊断

## 范围和结果

从 `ukisai/Swift-1.5-Qwen3.8-Flash-Next-NVFP4` 的 revision `3ff0520224f264a2d0ac4ab56ece8f2f13aadb38` 制作独立转换版。仅把 PLE 表从 BF16 转为 E4M3 FP8，主干 NVFP4、视觉权重、tokenizer 保持原样。原 checkpoint 保留，输出目录独立，无共享可写链接。

转换版已成功加载，并通过真实文本、工具、图片及 MCP 四任务并发检查。最终保留 NEXTN/MTP、524288 上下文、4 路并发和 655360 token pool。配置的最大上下文未做满长度压力测试；HiCache 保持关闭，便于此次同条件比较。

运行时镜像固定为 `ghcr.io/jpezzulli/sglang-rtxpro6000@sha256:7103728d3d5568e7fe56d684c179632dae5ccd62df48d20807e1cc779867b00c`。代码在本机维护，服务端只接收运行文件。

## 同条件输出和速度

固定任务集使用 temperature=0、seed=42、medium thinking；每例预热后测三次，每次清空请求缓存。功能检查、代码语法检查、纯速度检查分别统计。

| 指标                                  | BF16 PLE + MTP | FP8 PLE + MTP | FP8 PLE，关闭 MTP |
| ------------------------------------- | -------------- | ------------- | ----------------- |
| 原有功能检查                          | 30/36          | 34/36         | 34/36             |
| 新增代码语法/名称，temperature=0      | 未测           | 12/12         | 12/12             |
| 新增代码语法/名称，temperature=1      | 未测           | 12/12         | 12/12             |
| 固定 512-token 输出的 decode 中位速度 | 217.89 tok/s   | 219.35 tok/s  | 100.63 tok/s      |

速度为客户端流式采样估算，包含思考 token；不等于某个特定真实项目的完成速度。FP8 与原版速度基本持平，主要收益是主机内存减少。关闭 MTP 未改善这组总体通过数，速度约减半，因此保持开启。

原版失败包括 JSON 字符串被包成对象、乘法结果被写成表达式、区间漏合并。转换版也有 JSON 包装和区间逻辑错误。重复三次的小样本不能证明准确率提升。语法/名称检查不执行生成的代码，也不证明逻辑正确；中间思考的自我修正不由最终语法通过率衡量。

## 已修复的具体格式问题

在 thinking 与 string-valued JSON schema 同时使用时，模型思考已正确得到 `NEG_ZERO`，最终输出却出现 `">"` 或 `","`。MTP 开关两组都能复现。

原生 grammar 检查证明，即使 `any_whitespace=True`，根值前的空格和换行仍被拒绝。模型正常的换行被 mask 后，可能被迫选择另一个合法但错误的首 token。

`json-root-whitespace.patch` 在原 schema 前允许至多 8 个 RFC JSON 空白字符，保留原来的类型、枚举、字段、pattern 和递归约束；不改变普通文本、builtin JSON 或其他 grammar。`SGLANG_JSON_ROOT_WHITESPACE=0` 可恢复原行为。

验证结果：

- 32 项原生 grammar 正反例通过，包括空白上限、非法空白、错误类型、额外字段、递归和回退开关。
- 20 项真实 API 检查通过，其中原故障字符串在 thinking 开启下连续 10 次正确。
- 原始 token logprobs 显示修复后首 token 正常选择 `\n\n`，随后生成 `"NEG_ZERO"`。
- 独立格式/推理诊断 9/9 通过；其中区间用例改变了 reasoning effort，不能把它算作权重能力修复。

这是已复现的运行时格式处理缺陷修复。没有证据证明模型所有错字、符号错误或逻辑错误已经消除。

## 是否再把 PLE 搬入显存

主卡 ready 后仅余约 5.9 GiB 显存，PLE 表仍有 47.68 GiB；主机内存释放不会自动增加显存。现有运行配置仅支持 RAM/NVMe PLE 放置，没有部分显存缓存开关。

隔离微基准使用原生 gather 内核，160 MiB 合成 FP8 表和随机索引：16 行读取从 pinned RAM 改为 GPU，约节省 0.84 微秒；256 行约节省 8.20 微秒。该结果不代表真实缓存命中率或端到端加速。

进一步通过生产模型的 GPU profiler，提交四个请求并采集 30 个 scheduler step：74,996 次 GPU kernel 的累计耗时约 1.145 秒，其中 30 次 PLE gather 累计 4.106 毫秒，占约 **0.36%**；gather 中位数为 10.592 微秒，最大 1.391 毫秒（prefill）。累计 kernel 时间不等于墙钟时间，结果也不代表所有负载，但这次样本中 PLE 读取不是主要瓶颈。

因此未占用显存安全余量开发部分 PLE 缓存，保留现有上下文与并发容量。第二张显卡上的现有服务未调整。

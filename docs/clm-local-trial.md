# CLM 本地试验记录

本记录只评估 CLM 在本项目场景中的适用性，不把试验服务接入 Pi 的默认工作流。上游宣称的最高 9 倍提速，是它在特定候选动作排序任务相对 Jev 的结果，不代表任意代码分支或整个 Agent 的提速。参见 [CLM 官方仓库](https://github.com/Contrastive-LM/CLM)。

## 环境与方法

- CLM-v0.1-8B：冻结 Qwen3-8B-FP8 编码器、官方通用投影头；编码器上下文 2,048 token。FP8 是为 16 GB 显卡做的试验配置，并非官方 BF16 结果的复现。
- Flash Next：既有 `pennyroyal` 服务，原来的 MTP 推测解码和 512K 上下文保持不变。
- 标准答案：`server/plugin-grants.ts` 中 `PluginGrantsStore` 的实际返回值；每个场景都在独立临时目录运行。该源文件共 266 行、32 处 `if`。另有 12 个简单故障排查和动作选择冒烟场景。
- 模型调用按场景串行，记录每次端到端 HTTP 延迟。CLM 候选排序使用 `/v1/rank`，Flash Next 用 `/v1/chat/completions` 输出选项编号。以下 p50/p95 均为单次请求，不包含模型下载或进程启动。

| 场景 | 方法 | 答对 | 单次 p50 | 单次 p95 | 28 题请求时间总和 |
| --- | --- | ---: | ---: | ---: | ---: |
| 真实授权代码的 28 个分支场景 | 直接执行代码 | 28/28 | 0.091 ms | 0.297 ms | — |
| 相同场景，完整源码 | CLM 通用头 | 11/28 | 36 ms | 135 ms | 1.60 s |
| 相同场景，去除注释 | CLM 通用头 | 11/28 | 30 ms | 124 ms | 2.88 s（含一次异常慢调用） |
| 相同场景，完整源码 | Flash Next，最多 1,024 个输出 token | 28/28 | 2,101 ms | 3,181 ms | 58.82 s |
| 相同场景，完整源码 | 独立 Codex GPT-6 判读 | 28/28 | — | — | 约 6 s 阅读并一次性答题；非 HTTP 推理计时 |

Flash Next 初次用 512 个输出 token 时有 10 次没有给出最终答案；提高到 1,024 后，28 次都有答案且全部正确。完整源码约 3,450 个 Flash Next 输入 token，超过了此 CLM 试验的 2,048 token 编码上限；去注释后 CLM 仍只对 11/28。因此不能把低正确率单独归因于截断。12 个简单场景中，CLM 为 9/12、Flash Next 为 12/12。

这些是小规模、人工挑选的场景，不是上游 Jev 基准，也不能证明模型在其他任务上的总体优劣。Codex 的 28 题成绩是单次批量源码判读，耗时包含阅读，不能直接与逐题 HTTP 延迟比较。

## 结论和复跑

确定性的 `if`、权限规则和路径判断应继续直接执行源码：它既快又有可验证的结果。CLM 更适合有多个看似合理的候选动作或候选修复、且能从真实结果获得标签的排序任务。此次通用头的成绩不足以接管授权或审核。

```sh
node --import tsx tests/clm-branch-trial.mjs --oracle
CLM_RANK_URL=http://127.0.0.1:8700/v1/rank \
FLASH_URL=http://127.0.0.1:8000/v1/chat/completions \
node --import tsx tests/clm-branch-trial.mjs
```

`tests/clm-ranking-trial.mjs` 是 12 题动作排序冒烟脚本。所有样本使用虚构路径和无密钥文本；私有会话、模型权重、运行结果与服务配置不进仓库。

## 真实会话微调可行性试验

Pi 现有会话中约有 5,000 次工具调用。为测试官方 `choice` 微调流程是否能在现有设备上工作，曾从成功调用中提取 3,200 条“下一步选哪类工具”的记录，在本机清除网址、邮箱、IP、绝对路径和常见密钥格式后，按会话分成训练候选和留出集。训练候选 2,078 条来自 39 个会话；独立测试 1,122 条来自另 14 个会话。上游脚本再从训练候选中分出 220 条验证样本。仅训练投影头，冻结 Qwen 编码器；最佳权重出现在第 4 轮，约 1.3 分钟完成。

| 独立会话测试集 | 准确率 |
| --- | ---: |
| 始终选择最常见工具类别 | 74.15% |
| 未微调的通用 CLM 头 | 73.80% |
| 微调后的头 | 73.17% |

这只是训练流程的可行性试验，**不作为实际功能**：工具用途已在接口中声明，用户明确需要某项操作时应直接调用工具。记录中的“Agent 实际选了什么”也不是“正确选择”的可靠标签。这个数据集类别明显不均衡，且只有 53 个独立会话有可用样本；微调没有超过简单基线。试验权重和派生会话数据已清除，未接入服务。

对候选修复排序，仓库历史中有 119 个同时修改测试的修复提交，可以作为寻找样本的起点，但提交标题和通过测试的历史不能自动给多个候选修复贴可靠标签。应先为同一问题收集多个候选补丁，在隔离工作树里运行相关测试，按任务而非按补丁拆分训练与留出集，再与通用头及 Flash Next 比较。只有独立留出任务上既提高正确率又节省实际工作流时间，才考虑启用微调头。
